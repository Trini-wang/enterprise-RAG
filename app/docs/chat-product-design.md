# AI Chat、多轮对话与 Prompt 管理产品方案

> 文档状态：方案评审稿，不包含代码实现  
> 适用项目：知澜 Enterprise RAG  
> 更新时间：2026-08-23

## 1. 产品定位

本项目的 Chat 不应只是“文档检索结果展示”，而应是一个完整的 AI 对话产品。用户可以像使用通用 AI 助手一样进行问答、写作、总结、分析和连续追问；企业文档检索是 AI 在回答前自动使用的一种工具。

每轮对话遵循统一策略：

```text
用户消息
   ↓
结合对话历史生成检索问题
   ↓
先检索当前用户有权访问的知识库
   ├─ 有有效命中 → 知识增强回答，附文档引用
   └─ 无有效命中 → 使用所选大模型的通用能力正常回答
   ↓
流式返回并保存消息、模型、Prompt、检索决策和用量
```

“没有检索到文档”不等于“无法回答”。只有命中有效企业知识时，回答才声明依据知识库并展示引用；未命中时不虚构引用，也不把“未找到文档”作为最终答案。

## 2. 建设目标与范围

### 2.1 目标

- 支持通用 AI 聊天、持久化会话和多轮上下文。
- 每轮先检索文档，根据相关度自动决定是否注入知识上下文。
- 前端允许用户选择已启用的模型平台和具体模型。
- 知识增强回答展示可点击的来源；通用回答明确标识“未使用知识库”。
- 管理员可以管理模型平台、可用模型和 Prompt 的发布版本。
- 每次回答可追溯模型、Prompt 版本、检索结果、引用、耗时和 token 用量。
- Provider 与模型厂商解耦，优先支持 OpenAI-compatible 协议；OpenCode Zen 可作为首个配置的平台。

### 2.2 首期不包含

- 自主规划的复杂 Agent 和任意工具调用。
- 联网搜索、代码执行、图片生成、语音和多模态输入。
- Prompt A/B 实验、自动模型路由和复杂计费系统。
- 一个会话内的消息分支可视化；首期“重新生成”只展示最新结果。

## 3. 用户角色与权限

| 角色 | 能力 |
| --- | --- |
| 普通用户 | AI 对话、管理自己的会话、选择可用平台/模型、查看引用、使用已发布 Prompt |
| 管理员 | 拥有普通用户能力；配置平台和模型；创建、调试、发布、停用和回滚 Prompt |

权限原则：

- 会话和消息属于创建者，其他普通用户不可读取或修改。
- 用户只能选择管理员已启用且自己有权限使用的模型。
- API Key 由管理员在服务端配置，永远不返回给浏览器。
- Prompt 草稿仅管理员可见，已发布 Prompt 对被授权用户可见。
- 检索必须先按用户或工作空间权限过滤文档，再计算相关度。
- 管理员默认不能直接查看用户会话；如后续增加审计入口，应单独授权并记录日志。

## 4. 与现有前端的整合方案

当前前端位于 `app/static/`，是由 FastAPI 同源托管的原生 HTML、CSS、JavaScript 单页应用。现有视觉语言、响应式断点、JWT 存储和统一 `api()` 请求封装可以继续使用，不需要为了 Chat 引入前端框架。

### 4.1 导航结构调整

建议把主要导航调整为：

```text
概览
AI 对话          ← 新增，核心入口
知识检索          ← 保留，面向明确只想查文档的用户
文档管理
文件中心

管理
Prompt 管理      ← 仅管理员显示
模型管理          ← 仅管理员显示
用户管理

个人设置
```

“AI 对话”和“知识检索”职责不同：

- AI 对话：始终调用大模型，文档检索是回答前的自动工具，支持多轮。
- 知识检索：保留现有 `/query/search` 体验，只返回知识库命中内容，适合核对原文。

概览页的主输入框文案改为“问 AI 任何问题，也可以查询企业知识”，提交后进入 AI 对话；快捷开始同时保留“开始 AI 对话”和“检索知识”。

### 4.2 AI 对话页

沿用现有浅蓝色设计体系，在 `page-wrap` 内使用两栏主体，引用详情以抽屉呈现：

```text
┌────────────────┬────────────────────────────────────────────────┐
│ + 新建对话      │ 对话标题          [平台 ▼] [模型 ▼] [Prompt ▼] │
│ 搜索历史        ├────────────────────────────────────────────────┤
│                │ 用户消息                                        │
│ 今天            │                                                │
│  · 年假制度      │ AI 回答…… [1][2]                               │
│  · 帮我写邮件    │ 已使用企业知识 · 模型名称 · 1.8s                │
│ 最近 7 天       │                                                │
│ 已归档          │ ┌────────────────────────────────────────────┐ │
│                │ │ 给 AI 发送消息……                    发送 ↑ │ │
└────────────────┴─┴────────────────────────────────────────────┴─┘
                                                引用详情 → 右侧抽屉
```

关键交互：

- 新会话默认使用用户上次选择的平台和模型；管理员可配置系统默认值。
- 顶部先选平台，再联动显示该平台下已启用的模型。
- 平台或模型不可用时显示原因，并建议管理员配置的默认模型，不静默切换。
- 会话首次发送后记录默认平台和模型；用户切换时提示“后续消息将使用新模型”，每条回答仍记录实际模型。
- 消息生成时先显示“正在检索企业知识…”，随后进入“AI 正在回答…”。
- 知识命中时，回答底部显示“已使用企业知识”和引用数量；点击引用编号打开右侧抽屉。
- 未命中时显示弱提示“本次回答未使用企业知识”，但不打断正常聊天。
- 支持停止生成、复制回答、重新生成、反馈、修改标题、归档和删除。
- 失败时保留用户消息和失败状态，提供重试按钮，不生成伪造的助手消息。
- 空状态同时提供“询问企业知识”和“通用 AI 能力”两类示例。

### 4.3 Prompt 管理页

管理员页面由 Prompt 列表、版本化编辑器和调试区组成：

```text
Prompt 列表 → 基本信息 → System Prompt → 模板 → 检索策略 → 模型参数 → 调试 → 发布
```

编辑器支持：

- `System Prompt`：AI 身份、通用行为、安全边界和工具使用规则。
- “知识命中模板”：可使用 `{{question}}`、`{{history}}`、`{{context}}` 和 `{{citations}}`。
- “知识未命中模板”：可使用 `{{question}}` 和 `{{history}}`，明确允许模型使用通用能力回答。
- 检索参数：top_k、最低相关度、最多注入字符数。
- 模型参数：temperature、max_output_tokens；模型默认由用户选择，不固定在 Prompt 中。
- 在线调试：选择平台和模型，显示检索结果、命中判定、最终渲染 Prompt 和模型输出。
- 版本操作：保存草稿、发布、查看差异和从历史版本创建新版本。

已发布版本不可原地修改，保证历史回答可复现。

### 4.4 模型管理页

仅管理员可见，分为“平台”和“模型”两个层级：

- 平台字段：显示名称、适配器类型、Base URL、API Key、启用状态、请求超时。
- API Key 输入后使用服务端主密钥加密保存，仅允许覆盖或重设；接口只返回“已配置”状态，不回传明文。
- 提供“测试连接”，返回连通性、耗时和稳定错误信息。
- 模型字段：平台内模型 ID、展示名称、上下文长度、是否支持流式、是否启用、排序和默认标记。
- 用户端只接收公开模型目录，不接收 Base URL、API Key 或其他敏感配置。

### 4.5 响应式与前端状态

- 桌面端会话列表固定在对话页左侧，引用使用右侧抽屉。
- 小于现有 `820px` 断点时，会话列表改为抽屉；模型选择器压缩为一个组合按钮。
- 小于 `560px` 时，输入区固定在视口底部，引用详情使用全屏底部面板。
- `app.js` 的全局状态后续增加 `conversations`、`activeConversation`、`providers`、`models`、`selectedProviderId`、`selectedModelId` 和 `activeAbortController`。
- SSE 请求需要携带 Bearer Token，因此前端使用 `fetch()` 读取 `ReadableStream` 并解析 SSE，不使用原生 `EventSource`。
- 对增量文本做批量刷新，避免每个 token 都直接修改 DOM；模型输出按纯文本或经过严格白名单清洗的 Markdown 渲染。
- 用户最后一次平台/模型选择可保存在服务端偏好中；`localStorage` 只作为加载前的体验缓存，不作为权限依据。

## 5. 核心对话流程

### 5.1 新建会话并发送消息

1. 前端加载公开模型目录和已发布 Prompt，恢复用户最近选择。
2. 用户选择平台、模型和 Prompt 后输入消息。
3. 服务端校验用户是否有权使用所选平台、模型和 Prompt。
4. 创建或读取用户自己的会话，保存用户消息和本次运行记录。
5. 根据最近对话历史生成本轮检索查询；首期可以直接使用原问题，后续再增加查询改写。
6. 在用户有权访问的知识范围内执行检索。
7. 使用统一阈值策略判断是否“有效命中”，不能仅以结果列表非空作为命中。
8. 有效命中时，把结构化知识上下文和引用注入模型；未命中时，只发送 System Prompt、历史和当前问题。
9. 无论是否命中文档，都调用用户选择的大模型生成答案。
10. 通过 SSE 返回检索状态、文本增量、引用和完成信息。
11. 保存助手消息、实际模型、Prompt 版本、检索决策、引用、耗时和 token 用量。
12. 第一轮成功后使用当前模型生成 4–12 字的会话摘要标题；失败时使用首条问题的本地摘要兜底。

### 5.2 检索命中判定

现有 `DocumentStore.search()` 的分数只适合演示，不能直接作为产品阈值。产品实现应提供可校准的统一分数，并同时考虑：

- 最高相关度是否达到 `min_score`。
- 达标片段数量是否达到要求。
- 文档是否在当前用户可访问范围。
- 片段是否有足够有效内容，而非只有关键词重合。

建议首期检索 `top_k` 个片段，只注入达到阈值的结果；一个都未达标即进入通用聊天路径。阈值应通过评测集校准，不在代码中散落硬编码。

### 5.3 多轮上下文

- 历史消息由服务端读取，前端只提交当前消息和会话 ID。
- 在上下文窗口内，优先保留 System Prompt、当前问题和有效知识片段，再保留最近对话。
- 超出预算时先裁剪较早消息；后续可增加会话摘要。
- 检索问题可结合最近对话消解“它”“这个制度”等指代，但查询改写不得改变原意。
- 每轮允许切换模型；上下文裁剪按本轮模型的上下文长度计算。

### 5.4 重新生成与中断

- “停止生成”取消上游模型请求，并把运行状态记为 `cancelled`。
- “重新生成”复用原用户消息，但可选择新的平台、模型或 Prompt。
- 新回答不覆盖旧运行记录，以便审计和问题排查。
- 相同 `idempotency_key` 不重复创建消息或模型调用。

## 6. API 设计

业务接口均要求 `Authorization: Bearer <access_token>`。统一错误结构：

```json
{
  "error": {
    "code": "MODEL_NOT_AVAILABLE",
    "message": "所选模型未启用或无权使用",
    "request_id": "req_xxx"
  }
}
```

### 6.1 模型目录 API

#### `GET /ai/models`

返回当前用户可以使用的平台及模型，仅包含公开信息：

```json
{
  "providers": [
    {
      "id": "provider_zen",
      "name": "OpenCode Zen",
      "models": [
        {
          "id": "model_xxx",
          "model_key": "provider-model-id",
          "name": "模型展示名称",
          "supports_streaming": true,
          "is_default": true
        }
      ]
    }
  ],
  "default_provider_id": "provider_zen",
  "default_model_id": "model_xxx"
}
```

模型列表由后端配置决定，不允许普通用户直接填写任意 Base URL、模型名或 API Key。

### 6.2 Chat API

#### `POST /chat/completions`

非流式接口用于测试、Prompt 调试和内部集成：

```json
{
  "conversation_id": null,
  "message": "帮我写一封项目延期说明邮件",
  "provider_id": "provider_zen",
  "model_id": "model_xxx",
  "prompt_id": "prompt_default",
  "idempotency_key": "client-generated-uuid"
}
```

返回示例：

```json
{
  "conversation_id": "conv_xxx",
  "message": {
    "id": "msg_xxx",
    "role": "assistant",
    "content": "……",
    "status": "completed",
    "knowledge": {"searched": true, "used": false, "citations": []},
    "provider": {"id": "provider_zen", "name": "OpenCode Zen"},
    "model": {"id": "model_xxx", "name": "模型展示名称"},
    "prompt_version_id": "prompt_version_xxx",
    "usage": {"input_tokens": 320, "output_tokens": 180},
    "created_at": "2026-08-20T10:00:00Z"
  }
}
```

知识命中时，`knowledge.used` 为 `true`，引用项包含 `index`、`document_id`、`document_name`、`chunk_id`、`excerpt` 和 `score`。

#### `POST /chat/completions/stream`

请求体与非流式接口一致，响应为 `text/event-stream`：

- `conversation.created`：新会话创建成功。
- `message.created`：返回用户消息和助手消息 ID。
- `retrieval.started`：前端展示“正在检索企业知识”。
- `retrieval.completed`：返回 `used`、命中数量和可公开引用。
- `message.delta`：返回增量文本。
- `message.completed`：返回模型、Prompt、用量和耗时。
- `message.failed`：返回稳定错误码和是否可重试。
- `message.cancelled`：确认上游生成已取消。

不把供应商原始事件直接透传给前端，由 Provider 层统一转换。

## 7. 数据模型

### 7.1 `model_providers`

保存显示名称、`adapter_type`、Base URL、加密凭证引用、超时、启用状态和审计时间。API Key 不明文保存；优先使用环境变量或密钥管理服务，数据库只保存密钥引用。

### 7.2 `ai_models`

保存平台 ID、供应商模型标识 `model_key`、展示名称、上下文长度、默认输出上限、流式能力、启用状态、排序和默认标记。同一平台内 `model_key` 唯一。

### 7.3 `user_ai_preferences`

保存用户最近使用的平台、模型和 Prompt，只用于默认选择；实际权限仍在每次请求时校验。

### 7.4 `conversations`

保存 ID、用户 ID、标题、默认 Provider ID、默认模型 ID、Prompt ID、状态及创建/更新时间。

### 7.5 `messages`

保存会话 ID、角色、内容、`pending/streaming/completed/failed/cancelled` 状态、父消息、错误码和创建时间。

### 7.6 `message_runs`

每次模型调用一条记录，包含消息 ID、Provider ID、模型 ID、实际供应商模型名、Prompt 版本、检索是否执行、知识是否使用、阈值与命中数量、输入/输出 token、首 token 延迟、总耗时、请求 ID 和状态。

原始完整 Prompt 可能含敏感信息，默认不保存；确需保存时必须加密并设置保留期限。

### 7.7 `message_citations`

保存消息 ID、引用序号、文档 ID、片段 ID、文档名称快照、内容快照和相关度。仅当知识被实际注入模型时创建引用记录。

### 7.8 `prompts` 与 `prompt_versions`

- `prompts` 保存名称、描述、状态、默认标记和创建人。
- `prompt_versions` 保存不可变的 System Prompt、命中/未命中模板、检索参数、模型参数和发布时间。
- Prompt 不强绑定模型平台，保证同一个 Prompt 可配合不同模型使用。

新增表应通过 Alembic 迁移创建，不再仅依赖 SQLAlchemy `create_all`。

## 8. 技术架构

```text
现有静态前端 app/static
    ↓ REST + fetch/SSE + Bearer JWT
FastAPI Router
    ↓
Chat Orchestrator
    ├─ Conversation Service（历史、token 预算、状态）
    ├─ Prompt Service（版本解析、两种模板渲染）
    ├─ Retrieval Tool（权限过滤、检索、阈值判定）
    ├─ Model Registry（平台、模型、能力、用户权限）
    └─ LLM Provider Interface
          ├─ OpenAI-compatible Adapter
          ├─ 其他厂商 Adapter
          └─ 后续扩展
```

### 8.1 Provider 统一接口

Provider 对内至少提供：

- `complete(messages, model, parameters)`：非流式生成。
- `stream(messages, model, parameters)`：统一产出文本增量、用量和结束原因。
- `validate_model(model)`：校验模型是否可用。
- `health_check()`：后台测试平台连通性。
- 标准错误：鉴权失败、限流、超时、模型不存在、内容安全拒绝和上游异常。

Provider 隔离各平台的请求字段、流式协议、usage 格式和错误格式。Chat Orchestrator 不出现针对某个平台的条件分支。

### 8.2 一轮消息的编排规则

```text
鉴权与模型校验
  → 保存用户消息
  → 检索工具
  → 相关度判定
  → 选择命中或未命中 Prompt 模板
  → 计算模型上下文预算
  → 调用所选 Provider
  → 标准化流式事件
  → 保存回答、运行记录和引用
```

知识检索失败和知识未命中必须区分：

- 未命中：正常进入通用 AI 回答。
- 检索异常：可降级到通用回答，但元数据记录 `retrieval_status=failed`，前端提示“知识检索暂不可用”。
- 模型异常：不能用检索文本冒充 AI 回答，应返回可重试错误。

## 9. 与当前项目的衔接和前置改造

当前代码可以复用 JWT、SQLAlchemy、同源静态页面和现有视觉组件，但实现 Chat 前需要处理：

1. `/docs/*` 和 `/query/search` 当前没有登录鉴权，需要统一接入当前用户。
2. `DocumentStore` 仅保存在进程内，重启后文档与索引丢失，需要持久化。
3. 文档没有用户或工作空间归属，无法保证知识权限隔离。
4. 当前相关度算法不足以稳定判断“命中/未命中”，需要可评测、可配置的检索方案。
5. 项目缺少数据库迁移工具，应先引入 Alembic。
6. 需要集中式配置和密钥管理，不能把平台 API Key 下发到 `app.js` 或写入仓库。
7. 当前静态页面没有 Markdown 渲染依赖；实现时需选择安全渲染方式，默认禁止任意 HTML。

如果首期采用单一共享知识库，应在界面和部署文档中明确；它不等于已经实现企业多租户隔离。

## 10. 安全、稳定性与可观测性

- 按用户和平台限流，限制消息长度、历史轮数、输入预算和最大输出 token。
- API Key 仅在服务端读取，日志、接口和前端状态中均不得出现明文。
- 知识片段属于不可信输入，System Prompt 必须声明不得执行文档中的指令。
- 对模型输出进行安全 Markdown 渲染，过滤脚本、事件属性和危险链接。
- 日志记录请求、用户、会话、平台、模型、检索决策、耗时和状态，不记录 Token 或完整敏感正文。
- 上游超时、限流、鉴权和模型不存在使用不同错误码；只对安全的临时错误有限重试。
- 指标包括首 token 延迟、总耗时、成功率、检索命中率、检索降级率、各模型 token 用量与成本。
- 删除用户时清理会话、消息、运行记录和引用快照；保留策略可审计。

## 11. 分阶段交付

### 阶段 0：基础治理

完成 Alembic、配置/密钥管理、文档持久化、知识权限和检索评测。验收标准是重启不丢数据、不能越权检索、阈值能区分相关与无关问题。

### 阶段 1：AI Chat MVP

完成平台/模型配置、非流式 Chat、多轮历史、会话管理、自动检索双路径，以及前端 AI 对话页。验收标准：

- 文档相关问题使用知识并返回真实引用。
- 通用问题即使无文档也由所选模型正常回答。
- 用户能选择平台和模型，每条回答展示实际模型。
- 刷新后会话仍存在，跨用户访问返回 404。

### 阶段 2：流式与完整体验

增加 fetch/SSE、停止生成、失败重试、自动标题、会话搜索/归档、重新生成、响应式会话抽屉和 token 预算裁剪。

### 阶段 3：Prompt 与模型管理

完成 Prompt 双模板调试、发布、不可变版本和回滚；完成模型管理页面、连接测试、启停、默认模型和管理员审计日志。

### 阶段 4：运营与质量

增加反馈、检索与通用问答评测集、模型成本/延迟看板、Prompt A/B 实验和自动模型路由。

## 12. 实现前需要确认的产品决策

1. 知识库是所有登录用户共享，还是需要个人、部门或企业空间？
2. 首期启用哪些平台及模型？凭证采用环境变量还是外部密钥服务？
3. 普通用户能切换所有已启用模型，还是按角色配置权限？本方案默认可使用全部已启用模型。
4. Prompt 只由管理员管理，还是允许个人 Prompt？本方案默认仅管理员管理。
5. 检索异常时是否允许降级到通用 AI 回答？本方案默认允许，但必须提示。
6. 历史会话、原始问题、引用快照和用量数据的保留期限是多少？

以上决策确认后，再进入数据库迁移、后端接口和前端页面实现阶段。
